## 1. The one number that drives every decision

PassKit has two billing classes, and they are ~2.1× apart:

| | multi-use (membership, loyalty, gift) | single-use (coupon, ticket) |
|---|---|---|
| Examples | licence, loyalty card | voucher, event ticket |
| First tier rate (251–2,500) | $0.0450 | $0.0945 |
| When charged | **every month the record exists** | **once, at issuance** |
| Deleting it | stops the charge | refunds nothing |
| Auto-delete | 90 days after expiry date | 90 days after expiry date |

Platform fee is $39.50/mo (1 user) and includes 250 of *each* class free.

**Break-even.** A racer holding a licence pass for a year costs `12 × $0.0450 = $0.54`.
That same racer, ticketed per heat, costs `heats × $0.0945`.

> **A wallet licence pays for itself at ~5.7 heats per racer per year — roughly 3 visits.**

The ratio holds at every volume tier (both scale ~2.1:1), so 5.7 is the number regardless of scale.

**Consequence:** the licence pass must be **opt-in** ("Add to Wallet"), never auto-issued to
every racer in BMI. Opt-in self-selects the frequent guests who clear the break-even; auto-issuing
to a 12,000-row racer table would bill us monthly, forever, for people who came once in 2023.

## 2. Your instinct on combining licence + eTicket is right — and it's bigger than cost

Per-heat race eTickets are generated by cron for **every racer, every heat**
(`lib/race-tickets.ts` — one ticket per `(sessionId, personId)`, rendered at `/t/{id}`).
As PassKit single-use tickets that is the single most expensive thing we could possibly buy:

| race eTickets / month | single-use cost / month |
|---|---|
| 3,000 | $248 |
| 9,000 | $584 |

Versus holding licence passes, billed once a month no matter how many heats they run:

| licence passes held | multi-use cost / month |
|---|---|
| 500 | $11 |
| 2,000 | $79 |
| 5,000 | $186 |

The mechanism that makes the merge work: **pass updates and API calls are free and unlimited**
(explicitly listed as included in the platform fee). The Members API has `updateMember`,
`earnPoints`, `checkInMember` and a `metaData` map for arbitrary custom fields. So before each
heat the cron calls `updateMember` to write *next race: Sat 7:15 PM · Track 2 · Heat 4* onto the
pass the racer already holds, with a lock-screen push. Cost of that update: **$0.**

That converts a recurring per-heat single-use charge into a free field write on an
already-billed record. One pass per racer, for life, that reprints itself before every visit.

## 3. Recommended shape — three objects, not five

### A. Coupon campaign — "Vouchers" (single-use) ← **start here**
Mirrors the existing `vouchers` table 1:1.

- `externalId` = our `HPW…` code (already CSPRNG-minted, already the bearer instrument)
- `metaData` = `kind`, `batchId`, item labels
- `expiryDate` = our expiry → PassKit auto-deletes 90 days later, no cleanup cron
- **Barcode payload = `https://headpinz.com/v/{code}`** — the same URL the emailed QR already
  encodes (`voucher-mail.ts:64`)

**Why this is the right pilot:** zero kiosk changes. `classifyKioskCode` already pulls the code
back out of a `/v/{code}` path, so a wallet voucher scans at the kiosk today, through the
existing rail, with no new classifier verdict and no new precedence risk. And at current mint
volume (batches of ~5) it lands inside the 250/mo free allowance — the pilot costs the $39.50
platform fee and nothing else.

### B. Member program — "FastTrax Racing Licence" (multi-use) ← **next**
One pass per racer, opt-in.

> until it is.
>
> **The duplicate-`externalId` question is ANSWERED: members 409 exactly like coupons**
> (`cannot create member record. external id already exists`). Create-or-recover is therefore
> idempotent for members too — which matters far more here than for vouchers, because a duplicate
> member is a *recurring monthly* charge rather than a one-off. `GET
> /members/member/externalId/{programId}/{externalId}` recovers it; `PUT /members/member` pushes
> current state. Still unproven: **no wallet pass has ever been scanned at a physical kiosk.**

### Members API — five things that cost an hour each, none of them guessable

1. **A production program needs `passTypeIdentifier`.** Ours is `pass.com.fasttrax.booking`
   (`GET /certificates` → team 74Z5L3L3BT, valid to 2027-05-03). Without it: 400 *"you are
   creating a program in production, a validate pass type identifier needs to be provided"*.
2. **`status` is a repeated bitmask needing one value from TWO axes** — publish state AND
   object-creation state: `["PROJECT_PUBLISHED", "PROJECT_ACTIVE_FOR_OBJECT_CREATION"]`. It
   validates one axis per request, so you get two consecutive 500s each naming only the axis you
   are currently missing. (The voucher campaign carries the same pair.)
3. **Tiers are a SEPARATE resource.** The `tiers` array on `POST /members/program` is silently
   ignored and the program comes back with none — `POST /members/tier` against the program id is
   what binds the pass template. `tierIndex` **must be ≥ 1**: their Go `required` validator reads
   0 as unset, so `tierIndex: 0` fails as *"required"* and sends you hunting a missing field. The
   tier also carries its own `timezone`, separate from the program's `ianaTimezone`.
4. **`POST /images` derives a separate `appleLogo`, and Apple Wallet renders THAT, not `logo`.**
   Left alone it comes back 1:1. Point `appleLogo` at the wide image explicitly.
5. **Dressing a stock template inherits its images.** The "Your special card" membership template
   ships a `thumbnail`, and a GENERIC Apple pass renders a thumbnail on the right — so the licence
   showed stock art until `thumbnail` was explicitly cleared. Clear every slot you do not set.

### Apple layout constraints that decided this design

- **`strip` and `thumbnail` are mutually exclusive.** storeCard/coupon take a full-width strip;
  generic takes a right-side thumbnail; only eventTicket allows background + thumbnail. The
  licence uses **storeCard + strip**, which is what a racing photo wants — and is only available
  because the owner dropped the racer portrait (2026-08-04). A GENERIC pass silently ignores a
  strip, so the pass style must be set alongside it.
- **PassKit forces the header `logo` slot square** — upload 2072×660, get 660×660 back. A 3.14:1
  wordmark then letterboxes to a third of the height and Apple renders it small, which is why the
  brand read as missing. **The fix is to composite the mark into the strip artwork**, where we own
  the aspect ratio: 672px on a 1600px strip, centred (left-aligned would sit directly under
  Apple's own squared header logo and read as a duplicate).
- **Apple lays PRIMARY_FIELDS over the strip** — the same trap that printed the voucher offer
  across four kids' faces. The racer's name is a primary field here, so the strip's scrim is
  driven to 97% background by the bottom third where that name lands.
- **The strip is TEMPLATE-level, shared by every holder.** Fine for a logo and a generic track
  shot; it means nothing racer-specific can ever live in the artwork. Anything individual has to
  be a text field.

**Racer photos are not viable yet.** `GET /v2/bmi/person/{locationId}/{personId}?picture=true`
works and the payload is wrapped in `{success, data}`, but `pic` was **null on 4 of 5** records
probed (Eric included; only Curtis Stavich 713365 had one). Owner dropped the portrait 2026-08-04.

- `externalId` = BMI `personId`
- Tiers = **Rookie / Intermediate / Pro** — these already exist and are already detected by
  `api/cron/level-up-watch`, which today only sends an email. Pointing it at `updateMember`
  makes the pass itself level up, with a push. That is the feature that makes people add it.
- `metaData` = licence code, next race, waiver status, race credits
- Rolling expiry: push `expiry = last visit + 12 months` on every visit → lapsed racers
  auto-delete → **billing stops by itself.** Uses the vendor's own lifecycle instead of a sweep
  we'd have to write and monitor.
- **The licence code is PINNED at issuance, not re-read** — `tags[]` is append-only and the newest
  one changes every visit, but every tag resolves forever (§ 4 probe). Store the chosen code.
- **Show the code as large readable text**, deliberately breaking the voucher pass's "the barcode
  altText already prints it" rule (§ 7): racers TYPE this at BMI. Comment the reason in the
  template script so nobody "fixes" it.
- **"Valid until" needs `MAX(stops)`** over active `"License Fee"` memberships — one racer can
  carry dozens, nearly all expired (§ 4 probe).
- **Give this program its OWN preview ids.** The shared-campaign trade-off in § 8 is safe for
  vouchers because creation is idempotent and free; a preview-minted *member* is a recurring
  monthly charge production has to live with.
- The transport (`src/lib/api/passkit.ts`) and `wallet/platform.ts` need **zero** changes; the
  `PassKitProject` type in `src/config/passkit.ts` is coupon-shaped (`campaignId`/`offerId`/
  `templateId`) and needs widening to a discriminated union for a `programId` + tiers.

### C. Later, cost-gated — Game Zone / Deal Pack card
Only if the Intercard card genuinely gains something. Not in scope now.

### Explicitly NOT PassKit
- **Square gift cards.** Square already serves Apple Wallet *and* Google Pay free at
  `squareup.com/apass/gc/download/personalized/{id}` — already wired in `rewards.ts`. Paying
  PassKit to duplicate this would be a straight loss.
- **Per-heat race eTickets as their own passes.** See § 2.
- **Arena (laser/gel) eTickets.** Genuinely single-use and the guests aren't racers, so they
  can't ride the licence pass. Revisit only with real volume numbers in hand.

### The `tags[]` probe — run it before designing anything that prints a code

`apps/web/scripts/racer-tag-semantics-probe.mts` (read-only, 2026-08-04, live vs person 409523).
It settles what this section originally hand-waved as "your code":

- **`person.tags[]` is APPEND-ONLY and grows ~1 per visit — Eric has 31.** There is no stable
  "login code". `tags[0].tag` — what `license/lookup.server.ts` returns and what the level-up
  email links — is merely the newest, so **the code we show a guest changes every visit**. The
  `3tn4d694p6z94` quoted below is tag **#15**, from 2025-10-26; today's is `mgrm2g8o42wxc`.
- **Every one of the 31 still resolves, uniquely, to the correct person — including one last seen
  2023-09-25.** ~390 ms each, no collisions with other humans. So **a printed code never goes
  stale**, and old deep-links keep working forever. This was the largest unquantified risk in the
  licence-pass design and it is now closed.
- **Therefore: PIN THE PRINTED CODE AT ISSUANCE** (store it on the pass row) and never re-read
  `tags[0]` on sync. Re-reading would churn the number on the pass after every visit and break the
  muscle memory of the racers who type it — for no benefit, since the old one still works.
- Tag shapes vary: mostly 13-char lower-alnum, some **6-digit** (`973273`), and **the SMS-Timing
  member-QR GUID is itself a tag** (`3f59bc35-…`) — readable, but with no special status. `races`
  is computed as `tags.length`, which is why it tracks visits at all.
- **Licence expiry needs MAX, not first-match**: 35 `"License Fee"` memberships on one person, 34
  expired and one live to 2026-10-31. `personHasActiveLicense`'s `.some()` is correct for a
  boolean; § 3B's "valid until" must take the max `stops` over active rows.

The original probe, kept because it is what proved the rail in the first place:

```
GET /api/headpinzftmyers/search/person?token=3tn4d694p6z94 → 200
[{"localId":"409523","description":"Eric Osborn (2/12/1991) … phone: 2397762044 …
  Last seen: 7/1/2026 Memberships: … Qualified Intermediate, Qualified Pro"}]
```

One exact hit, ~1 s. This is the *same call* `lookupMemberMatches()` already makes for the
SMS-Timing member QR. So:

| Layer | State |
|---|---|
| licence code → person | **Works today.** No new integration. |
| person → today's reservation | **Missing for check-in** — but `getReservationsByContact` already exists in `checkin/server.ts`, and the phone is right there in the search description. Small, contained. |
| entry-screen scan routing | **Needs a new branch.** A bare 13-char licence code matches `SHORT_CODE_RE` (6–16 alnum), so `classifyEntryScan` calls it a `shortcode`, tries the reservation index, misses, and dumps the guest into the coupon screen. |

That third row is the real work, and the file that owns it already documents the trap it falls
into: `entry-scan/classify-entry.ts` is explicitly about **most-specific shape first, greedy
catch-alls last**. A `licence` verdict has to be ordered ahead of the short-code catch-all, and
it is not a pure shape decision (13 alnum chars is also a legal promo code), so it likely lands
on the existing `resolve-then-code-entry` pattern rather than a hard verdict.
_(Superseded — see the status box at the top of this section. Wrapping the code in a URL made it
a hard verdict instead.)_

**None of this requires PassKit.** Licence-at-check-in is worth doing on its own merits; the
wallet pass is just the nicest place to put the barcode once it works.

## 5. Non-negotiables this integration inherits

- **Neon stays source of truth** (CLAUDE.md hard rule). Mint the voucher in Neon *first*, then
  best-effort create the PassKit coupon. PassKit's redemption state must **never** gate a redeem
  or a check-in — we mirror `redeemCoupon` *after* our own claim succeeds. A PassKit outage must
  degrade to exactly today's behaviour.
- **Barcode payload must be a URL our existing classifier already understands.** Anything else
  forks the scan rail.
- **EN + ES for every guest-facing string on a pass**, same as kiosk copy.
- **Flags are kill switches only.** If there's a `PASSKIT_SYNC` flag it defaults ON and exists
  solely to stop the sync.
- **Confirm the multi-use billing question with PassKit in writing before scaling past the
  pilot.** `passkit.com/pricing/faq` says *"created minus deleted during that month"* (reads
  like new-in-month) but also *"renew monthly until deleted"*, and the help-centre pricing page
  says the count is total-created-minus-total-deleted. If it's new-in-month the licence pass is
  dramatically cheaper than modelled here; if it's cumulative-alive, § 1 stands. Do not guess.


**JWT gotcha, measured live.** HS256, claims `{uid: <key>, iat, exp}`, `Authorization: <jwt>`
(bare token, no `Bearer` prefix). `exp` must be ≤ 60 s out. The trap:

| `iat` | result |
|---|---|
| `now` | 401 `Token used before issued` — their clock ran 3 s behind ours |
| `now − 5` … `now − 60` | **200** |
| `now − 75` and older | 401 `jwt was issued too long ago` |

Use `iat = now − 30`, `exp = now + 50`. Sign a fresh JWT per request; do not cache.

`EVENT_TICKETING` template ("My Production") from PassKit's onboarding. Clean slate.

### Design — signed off 2026-08-03

Face: HeadPinz logo, laser-tag photo strip, then ONE row — `YOUR VOUCHER / 2× Laser Tag + 200
Tokens` left, `EXPIRES / Aug 3, 2027` right — then the QR with the code as its altText.

Three things that made the difference, all non-obvious:

1. **Never use `PRIMARY_FIELDS` on a pass with a strip image.** Apple lays them OVER the strip.
   The first version printed the offer in giant white text across four kids' faces, with its own
   label rendering *underneath* its value. Everything visible belongs below the strip.
2. **No CODE field on the face** (owner: _"do we really need code in line text when we have it
   under qr"_). The barcode's altText already prints it. Same for locations — they went to the back
   where a full sentence fits instead of truncating to "HeadPinz Fort Myers…".
3. **Flatten every image onto the pass background.** PassKit composites transparent PNGs onto
   BLACK, so a transparent logo renders as a dark box on a coloured card. Also bias the strip crop
   to the top — sharp's `position: "attention"` sliced the tallest kid's head off.

**Voucher volume measured: 32 rows all-time, all in the last 30 days.** Comfortably inside the
250/mo free single-use allowance, so the pilot costs the platform fee and nothing more. This
also means § 1's licence-pass break-even is the only number that can actually move the bill.

### Gotchas that cost real time (all now encoded in the script header)

1. **Region is pub2**, not the pub1 in every doc example.
2. **JWT `iat` must be backdated ~30 s**, and the header is `Authorization: <jwt>` with **no
   `Bearer` prefix**.
3. **Campaign `status` is a repeated bitmask.** A scalar gives a proto *syntax* error, not a
   bad-enum error, which sends you hunting the wrong problem. Needs one of
   `{PROJECT_ACTIVE_FOR_OBJECT_CREATION, PROJECT_DISABLED_FOR_OBJECT_CREATION}` **and** one of
   `{PROJECT_DRAFT, PROJECT_PUBLISHED}`. `PROJECT_PUBLISHED` = production and additionally
   requires `passTypeIdentifier`.
4. **Template field `uniqueName` must be prefixed** `meta.` / `person.` / `universal.` /
   `protocol.` / `custom.`.
5. **Images: `POST /images` with `{imageData: {icon, logo}}`** (slot-keyed base64), minimum
   **660×660 on every slot**. Without an icon the pass URL 500s with no useful message.
6. **`custom.foo.label` / `custom.foo.value` in the rendered pass.json are NOT a bug.** They are
   Apple localization keys, resolved in `en.lproj/pass.strings`. Verify there, not in pass.json —
   I nearly filed this as broken. It is also the hook for the EN+ES rule: a second `.lproj`
   comes from `localizedLabel` / `localizedDefaultValue`.
7. **Always read the barcode back.** A wrong `${...}` name renders literally — the first attempt
   shipped `https://headpinz.com/v/missing: coupon.externalId`, which returns 200 everywhere and
   would only have failed at a kiosk. `${coupon.externalId}` does not exist; drive the payload
   off per-coupon `metaData` (`${meta.redeemUrl}`) instead.

- Move `PASSKIT_VOUCHER_CAMPAIGN_ID` / `_OFFER_ID` to env, **different ids for preview vs prod**,
  so preview traffic can't mutate real guest passes.
- **Scan the pass at a real kiosk.** The barcode payload is verified byte-for-byte, but nothing
  has been through a physical reader.
- Spanish `.lproj` for the pass copy.

## 8. Voucher rollout plan

### Do we issue a pass before the guest clicks? NO.

**Single-use passes are billed at issuance, not at install** (§ 1). Pre-issuing a coupon for every
voucher we mint bills us for every voucher — including the ones whose email is never opened. Issue
lazily, on the tap, and we only pay for passes guests actually wanted.

Two probes make lazy issuance safe rather than fiddly (both run live 2026-08-03):

| Question | Answer |
|---|---|
| Does a duplicate `externalId` in one campaign create a second billed pass? | **No — 409** `duplicate entry. external id already exists`. Double-tapping "Add to Wallet" cannot double-bill. |
| Can we recover the pass id without storing it? | **Yes** — `GET /coupon/singleUse/coupon/externalId/{campaignId}/{externalId}` → 200 with the full coupon. |

So the route is create-or-recover, and it is naturally idempotent because `externalId` is our own
`HPW…` code. No lock, no reservation, no cleanup job.

### PR1 — lazy-issue route + entry points

**`GET /v/[code]/wallet`** (route handler, no page). `/v/` is already registered in
`SHARED_TOP_LEVEL_ROUTES` (`middleware.ts:574`), and `startsWith("/v/")` means a nested segment
inherits it — **no middleware change**, so HeadPinz guests don't 404.

1. Normalize + shape-check with `isNativeVoucherCode` — reject before any I/O.
2. Load the row from Neon. Missing → 404.
3. **Refuse a voided or already-claimed voucher** and redirect to `/v/{code}`, which already
   explains the real state. This is the whole reason to own the route instead of putting a static
   PassKit SmartPass link in the email: a link signed at mint time cannot know the voucher was
   voided afterwards, and we have already been burned by exactly that
   (deal-pack: _"cart claims never checked voided/expired — a voided voucher still worked"_).
4. `POST /coupon/singleUse/coupon` with `externalId` = code, `metaData` built from the row
   (`voucherValue` from the `items` jsonb, `expires`, `code`, `redeemUrl`).
5. On **409**, `GET …/externalId/{campaign}/{code}` to recover the existing pass.
6. Persist `passkit_coupon_id` on the row — best-effort; step 5 means correctness never depends
   on it.
7. Redirect by user agent: iOS → `…/{id}.pkpass`, Android → `…/{id}.gpay`, anything else →
   `…/{id}` (PassKit's own landing page). Saves the guest a tap on the two platforms that matter.
8. `voucher_events` row: `wallet_pass_issued`.

**Kill switch** `PASSKIT_SYNC`, default ON (`!== "false"`). Off = the route 302s to `/v/{code}`.
Per the flags rule this exists only to turn the feature off, never to gate its release.

**Entry points**, all pointing at `/v/{code}/wallet`: an "Add to Apple / Google Wallet" button on
the `/v/{code}` page, the same button in the voucher email (`game-cards/service/voucher-mail.ts`),
and the SMS link. The existing QR stays — it is the fallback for guests who don't use Wallet.

**Schema:** `ALTER TABLE vouchers ADD COLUMN passkit_coupon_id text` (nullable).

**Env — credentials only** (all three environments):
`PASSKIT_API_URL`, `PASSKIT_API_KEY`, `PASSKIT_API_SECRET`.

Campaign / offer / template ids are **hard-coded in `src/config/passkit.ts`**, not env (owner
decision 2026-08-03: "you will have more"). They are stable identifiers, not secrets — useless
without the key, they never rotate, and several more programs are queued (racing licence, deal
packs, arena tickets). Three env vars per program × three environments is nine entries to keep in
sync, where a single typo fails at runtime in a way nobody notices until a guest taps a button. In
code they are reviewable, diffable and typo-checked by `tsc`.

Consequence accepted: preview shares production's campaign. Safe **for vouchers specifically**
because a pass is keyed on `externalId` = the real `HPW…` code and creation is idempotent, so a
preview tap produces the same single pass production would. Do not extend that reasoning to a
program where preview could mint objects production has to live with.

### PR2 — lifecycle mirroring

Neon stays the source of truth; PassKit is a downstream sync that must never gate anything.

- Our claim succeeds → `redeemCoupon` so the pass visibly flips to redeemed. **After** the claim,
  fire-and-forget, logged. A PassKit outage must not block a guest at a kiosk.
- We void in Neon → `voidCoupon`.
- Neither call's failure unwinds our own state.

### PR3 — Spanish

Pass copy is guest-facing, so the EN+ES rule applies: `localizedLabel` / `localizedDefaultValue`
produce a second `.lproj` in the pkpass (this is the same mechanism behind the `custom.foo.label`
keys in § 7). Also the button copy on `/v/{code}` and in the email.

Confirmed on device: a metadata write reaches an already-installed pass without a re-add. PR2 is

## 9. Partial redemption — "redeem half, update remaining"

### Our vouchers are already multi-leg, and claims are already per-leg

`vouchers.items` is a jsonb ARRAY and `voucher_claims.item_index` records which leg was taken.
The demo voucher is four legs: `laser-tag ×1`, `laser-tag ×1`, `100 bonusTokens`, `100 bonusTokens`.
So a guest burning one laser tag and one game card, then coming back in a month for the rest, is
already a supported state in Neon. Nothing new is needed in the ledger — only a way to *show* it.

### PassKit coupon status is BINARY, so do not model remaining with it

`CouponStatus` is `UNREDEEMED | REDEEMED` — there is no partial. Verified in the gRPC definitions.
So:

- **Keep the coupon `UNREDEEMED` while any leg is unclaimed.** Show what's left in a metadata field.
- **Call `redeemCoupon` only when the LAST leg is claimed.**
- Set the offer's currently-empty **`afterRedeemPassTemplateId`** to a second, visually spent
  template so a fully-used voucher looks used instead of looking live.

The alternative — a multi-use membership pass with `points`/`burnPoints` as the remaining balance —
fits the semantics better but bills **monthly per pass** (§ 1) instead of once at issuance. Not
worth it for a voucher that is typically consumed within weeks.

### The pass is a display surface, never the ledger

`voucher_claims` is the truth. The pass renders a projection of it. If a push fails the guest sees
stale text while the kiosk still redeems correctly — that is the safe failure direction, and it is
the same rule as everywhere else here: Neon first, PassKit downstream, never a gate.

**Corollary: never compute remaining on the client or from the pass.** Recompute from
`items` minus open `voucher_claims` on every write.

### Label is "REMAINING" in both states

An untouched voucher's remaining *is* everything, so the face never has to switch wording — one
field, one binding, no conditional design. Applied to the live template 2026-08-03. Also set
`changeMessage: "Voucher updated: %@ left"` on that field, which is what Apple surfaces on the
lock screen when the value changes.

### PR2 (revised) — mirror claims to the pass

One helper, called from wherever a claim is written or released:

```
syncVoucherPass(code):
  row     = vouchers[code]                        # Neon, source of truth
  claimed = voucher_claims[code] where released_at is null
  left    = items minus claimed, by item_index
  if left is empty:  redeemCoupon(externalId=code)     # flips to the spent template
  else:              updateCoupon(metaData.voucherValue = summarise(left))
```

- Fires **after** our own claim commits, fire-and-forget, logged to `voucher_events`.
- A **released** claim (abandoned cart) must re-add the leg — `released_at` already exists for this,
  and the sweep that releases claims has to call the same helper or the pass under-reports forever.
- No pass yet issued (guest never tapped Add to Wallet) → no-op. Cheap: skip on
  `passkit_coupon_id IS NULL` rather than calling PassKit to find out.

### Push propagation works — and PassKit's own telemetry lies about it

**CONFIRMED ON DEVICE 2026-08-03.** A metadata write reached an already-installed pass, no
delete-and-re-add. Live mirroring is real, so PR2 ships and § 3B's licence pass is viable.

**Do not use these fields to check whether a push fired — they are not wired for coupons:**

| Field | What it did | Reality |
|---|---|---|
| `passMetaData.lastUpdatedAt` | stayed `null` across ~8 writes | pass updated anyway |
| `passMetaData.lifecycleEvents` | never gained an update event; stuck at `["RENDERED","INSTALLED_APPLE","APPLE_PASS_CREATED","GOOGLE_PAY_RECORD_CREATED"]` | pass updated anyway |
| `coupon.updated` | DID move on every write | the only field that tracks anything |

Chasing `lastUpdatedAt` cost real time and nearly got the whole mirror written off as unshippable.
**The only reliable check is a device**, or `coupon.updated` for "did my write land".

The alert a guest actually sees comes from the field's `changeMessage` (set to
`"Voucher updated: %@ left"` on the REMAINING field), which Apple surfaces on the lock screen when
the value changes. There is **no REST endpoint for an arbitrary push** — `…/coupon/{id}/push`,
`…/coupon/push`, `/passes/{id}/push`, `/push` and `…/coupon/notify` all answer 404/501, so
free-text pass messages are gRPC or portal only. Field-change alerts are the mechanism we have.

### Latent bug to fix before rollout

The offer was created with `couponExpirySettings.couponExpiryType = AUTO_EXPIRE_OFFER_END_DATE`,
so coupon expiry is driven by the **offer's** end date. It looks correct today only because the
offer end date happens to equal this one voucher's expiry. Real vouchers have per-row `expires_at`,
so the offer must use **`EXPIRE_ON_VARIABLE_DATE_TIME`** and let each coupon's own `expiryDate`
govern. Otherwise every voucher inherits one shared expiry — and since PassKit deletes records 90
days after expiry, a wrong expiry also means wrong retention.
